# 1. Бизнес-анализ (Business Understanding)

> PRism — AI-сервис для автоматического ревью Pull Request'ов, который выявляет архитектурные антипаттерны, нарушения SOLID, 
> скрытые N+1-запросы, race conditions и security-мисконфигурации, недоступные обычным линтерам.

---

### Проблема

Команды разработчиков теряют время и качество кода из-за **неравномерного и поверхностного code review**: 
ревьюеры не замечают архитектурных проблем, которые линтеры не покрывают, а PR-очередь растёт быстрее, чем люди успевают её разбирать.

Конкретные болевые точки:

- ревьюер видит код вне контекста кодовой базы и не замечает, что этот фрагмент уже нарушает паттерн в трёх других модулях;
- линтеры (ESLint, Pylint, Checkstyle) ловят синтаксис и стиль, но не логические и архитектурные антипаттерны;
- GitHub Copilot и аналоги предлагают автодополнение, но не анализируют смысловую корректность PR в целом;
- технический долг накапливается незаметно: каждый отдельный PR выглядит нормально, а вместе они деградируют архитектуру;
- senior-разработчики тратят до 20–30% времени на рутинный ревью, который мог бы делать автомат.

---

### Основная идея продукта

PRism — это сервис, интегрированный в CI/CD через GitHub App, который анализирует каждый входящий Pull Request и автоматически оставляет review-комментарии к конкретным строкам кода с объяснением проблемы и рекомендацией по исправлению.

Под капотом сервис выполняет **двухуровневый анализ**: сначала файн-тюненная модель на базе CodeBERT классифицирует фрагменты диффа по типу антипаттерна, затем RAG-пайплайн подтягивает релевантный контекст из кодовой базы репозитория — это позволяет выявлять проблемы, которые видны только в связке с остальным кодом (например, N+1-запрос внутри метода, который вызывается в цикле в другом модуле). Финальный комментарий генерирует LLM, уже зная тип проблемы и контекст — это разделение ответственности: модель классифицирует, RAG добавляет контекст, LLM формулирует.

**Возможности PRism:**

- интеграция через GitHub App: webhook на событие `pull_request`, автоматический запуск анализа без ручных действий;
- классификация фрагментов кода по 8 классам антипаттернов с confidence score;
- RAG-обогащение контекстом: поиск релевантных участков кодовой базы через векторный поиск по эмбеддингам;
- генерация inline review-комментариев на GitHub с объяснением и конкретным советом по исправлению;
- поддержка **Java** на MVP; Python, TypeScript/JavaScript и другие языки — пост-MVP (roadmap);
- dashboard с историей PR и динамикой технического долга по репозиторию.

---

### Бизнес-цели

- снижение времени на рутинный code review для senior-разработчиков (target: −30%);
- рост метрик качества кода в репозиториях, использующих сервис (снижение плотности антипаттернов в новых PR);
- удержание команд на подписке (retention): сервис полезен на каждом PR, что создаёт высокую частоту использования;
- рост числа репозиториев, подключённых через GitHub App (viral loop: один разработчик устанавливает — вся команда видит комментарии).

---

### Целевая аудитория

- команды разработчиков от 3 до 50 человек, активно использующие GitHub и практикующие code review;
- технические лиды и senior-разработчики, отвечающие за качество кодовой базы;
- стартапы и продуктовые компании, у которых нет выделенного architect-роли, но есть растущий технический долг;
- проекты на **Java** как первичный языковой фокус MVP; Python, TypeScript и др. — при расширении датасетов и продукта.

### Существующие решения на рынке

Инструменты для анализа кода делятся на **статические анализаторы**, **AI-дополнения** и **специализированные review-сервисы**.

**Статические анализаторы** (SonarQube, Pylint, ESLint, Checkstyle) покрывают синтаксические ошибки, code smells по готовым правилам и метрики сложности. Они не понимают семантику и архитектурный контекст: правила либо написаны вручную, либо основаны на паттернах AST — они не «видят», что конкретный вызов в этом месте кода создаёт N+1 с учётом flow приложения.

**AI-дополнения к IDE** (GitHub Copilot, JetBrains AI, Tabnine) ориентированы на генерацию и автодополнение, а не на критический анализ PR. Copilot Code Review — недавняя функция, но она работает как generalist-модель без специализации на архитектурных антипаттернах и без контекста кодовой базы.

**Специализированные сервисы** ближе всего к PRism:

- **CodeClimate** — метрики сложности и дублирования, интеграция с GitHub; слабее именно на смысловых и архитектурных проблемах, нет LLM-объяснений;
- **DeepCode / Snyk Code** — сильный в security-уязвимостях, но не в SOLID-нарушениях и архитектурных антипаттернах;
- **Codacy** — агрегатор правил из множества линтеров, coverage; та же граница: правила, а не понимание смысла;
- **CodiumAI (Qodo)** — генерация тестов по коду; другой фокус, не ревью антипаттернов.

---

### Чем PRism заметно сильнее типичных альтернатив

PRism закрывает слепое пятно между линтером и человеком-ревьюером: **смысловой и архитектурный анализ с учётом контекста всей кодовой базы**, а не только фрагмента диффа.

**В чём конкретно отличие:**

- **Специализированная классификационная модель, а не generalist.** CodeBERT файн-тюненный на датасете из реальных PR-комментариев знает разницу между `SOLID_VIOLATION` и `MISSING_ERROR_HANDLING` — это не та же задача, что автодополнение строки.

- **RAG-контекст из репозитория.** Перед тем как вынести вердикт, сервис ищет релевантные участки кодовой базы: вызовы данного метода, определения классов, похожие паттерны. Это позволяет видеть антипаттерны, невидимые при изолированном анализе одного файла.

- **Разделение «что» и «как».** Модель классифицирует тип проблемы; LLM только формулирует объяснение и совет. Это предотвращает галлюцинации LLM в вынесении вердикта и делает систему проверяемой: confidence score классификатора отображается явно.

- **Inline GitHub-комментарии с конкретной строкой.** Вывод не абстрактный отчёт, а review-комментарий к конкретной строке PR — ровно в том же UX, где работает команда.

## 1.1 Текущая ситуация

### Ресурсы и инфраструктура

**Инфраструктура (MVP)**
- Облако: `Hetzner` или `Yandex Cloud` — один провайдер для снижения операционной сложности.
- Подход: container-first (`Docker Compose` на MVP, переход на `Kubernetes` при необходимости масштабирования).
- Vector store: `Qdrant` (self-hosted, бесплатно).
- Эксперименты: `MLflow` (self-hosted или MLflow на HuggingFace Spaces).
- Базовая модель: `microsoft/codebert-base` — открытая, доступна на HuggingFace, лицензия MIT.

### Данные

**Ядро датасета — реальные PR-комментарии из GitHub:**

- **GitHub API + PyDriller** — парсинг публичных репозиториев: пары (фрагмент кода из диффа → review-комментарий к нему). Целевой объём: 40 000–60 000 аннотированных сниппетов.
- **CodeSearchNet** — корпус кода на 6 языках с описаниями; используется для предобучения эмбеддингов и как источник негативных примеров (класс `CLEAN`).
- **CWE / OWASP датасеты** — для класса `SECURITY_MISCONFIG`; публично доступны.
- **Ручная верификация разметки** через Label Studio: подмножество ~3 000 примеров размечается вручную для проверки межразметчикового согласия (Cohen's kappa ≥ 0.7 как порог качества).

**Классы антипаттернов (целевые метки):**

| Класс | Описание |
|---|---|
| `SOLID_VIOLATION` | God Object, нарушение SRP, жёсткая связность |
| `N_PLUS_ONE` | запросы к БД или внешние вызовы внутри цикла |
| `RACE_CONDITION` | shared state без синхронизации |
| `SECURITY_MISCONFIG` | hardcoded secrets, небезопасные зависимости, SQL injection |
| `MISSING_ERROR_HANDLING` | непойманные исключения, игнорируемые ошибки |
| `EXCESSIVE_COMPLEXITY` | цикломатическая сложность > порога, глубокая вложенность |
| `DEAD_CODE` | unreachable branches, неиспользуемые переменные и методы |
| `CLEAN` | нет антипаттернов (балансировочный класс) |

---

### Риски и как мы их закрываем

- **Дисбаланс классов.** `RACE_CONDITION` и `SECURITY_MISCONFIG` встречаются редко, `CLEAN` — очень часто. Закрываем: взвешенный loss (`class_weight='balanced'`), oversampling редких классов через синтетическую генерацию примеров с помощью LLM (с верификацией), оценка по F1-macro а не accuracy.

- **Шум в автоматической разметке.** Не все PR-комментарии указывают на реальный антипаттерн — многие это стилевые замечания или вопросы. Закрываем: фильтрация комментариев по ключевым словам и паттернам (regex pre-filter), ручная верификация выборки, Cohen's kappa как обязательный порог.

- **Контекстная зависимость.** Один и тот же фрагмент может быть проблемой в одном контексте и нормой в другом. Закрываем: RAG-обогащение на inference; в обучающем датасете фиксируем не только сниппет, но и имя файла/модуля как дополнительный признак.

- **Scope creep.** Желание добавить поддержку Go, Rust, поддержку GitLab, анализ истории репозитория — всё это за рамками MVP. Закрываем: жёсткий scope на **Java** как единственный язык анализа в MVP; Python, TypeScript, Go, Rust и др. — вне MVP до отдельного решения; один provider (GitHub), один тип вывода (inline PR комментарии).

## 1.2 Решаемые задачи с точки зрения аналитики (Data Mining Goals)

### Выбор постановки для MVP (фиксируем явно)

**Вариант A (MVP): многоклассовая классификация фрагментов кода.**
Из сниппета диффа получаем метку одного из 8 классов + confidence score. Офлайн-метрики: **F1-macro** (основная), **Precision и Recall по каждому классу**, **confusion matrix**. Threshold по confidence задаётся отдельно для каждого класса: комментарий публикуется только при confidence выше порога, чтобы не спамить ложными срабатываниями.

**Вариант B (не MVP): multi-label классификация.**
Один фрагмент может содержать несколько антипаттернов одновременно. Переход на multi-label требует отдельной разметки и иных метрик (micro-F1, Hamming loss) — откладывается на пост-MVP.

---

**Связь North Star с офлайн-метриками (цепочка гипотез):**

улучшение **F1-macro** классификатора → более точные и релевантные inline-комментарии → выше доля принятых Review Suggestions → снижение плотности антипаттернов в последующих PR от той же команды → снижение времени ревью для senior-разработчиков → retention команды на подписке.

Это конструкция для приоритизации экспериментов, а не жёсткая импликация.

**Концептуальная схема контура данных (MVP):**
`PR diff` → **чанкинг по функциям/методам** → **CodeBERT-классификатор** (тип антипаттерна + confidence) → **RAG** (релевантный контекст из кодовой базы) → **LLM** (формулирует inline-комментарий) → **GitHub API** (публикует review).

---

### Задача 1. Классификация антипаттернов (Core ML Model)

Из фрагмента кода (функция или метод из PR-диффа) получаем **метку класса + confidence score**. Это центральная ML-задача проекта.

**Модели (порядок эксперимента):**
1. Baseline: TF-IDF + Logistic Regression / Random Forest — быстрая точка отсчёта.
2. Основная: fine-tune `microsoft/codebert-base` на задачу многоклассовой классификации (classification head поверх [CLS]-токена).
3. Сравнение: `microsoft/graphcodebert-base` (учитывает data flow), `salesforce/codet5-base` — эксперименты по F1-macro и inference latency.

**Офлайн-метрики:** F1-macro (основная), Precision/Recall по каждому классу, MCC (Matthews Correlation Coefficient) как устойчивая к дисбалансу метрика. Отдельно: inference time на CPU/GPU (важно для SLA сервиса).

**Данные:** GitHub PR-комментарии (§1.1), разбиение 70/15/15 train/val/test, стратификация по классам. Test set не используется до финального выбора модели.

---

### Задача 2. RAG-контекст из кодовой базы

К каждому классифицированному фрагменту подтягивается релевантный контекст из репозитория для обогащения финального комментария.

**MVP:** чанкинг репозитория по функциям/классам → эмбеддинги через encoder CodeBERT → хранение в Qdrant → top-k retrieval по косинусному расстоянию.

**Оценка качества RAG:** MRR (Mean Reciprocal Rank) и Recall@k на небольшом размеченном вручную eval-сете вопрос-контекст пар; продуктовый proxy — доля комментариев, принятых (resolve) без дополнительных вопросов от разработчика.

**Пост-MVP:** переиндексация при push в main, инкрементальное обновление индекса, fine-tuning retrieval-модели на парах (антипаттерн → релевантный контекст).

---

### Задача 3. Генерация inline-комментария

LLM (через API: OpenAI GPT-4o mini или Anthropic Claude Haiku — по критерию latency/cost) получает на вход: тип антипаттерна от классификатора + извлечённый контекст из RAG + исходный сниппет. На выходе — читаемый комментарий с объяснением проблемы и конкретным советом по исправлению.

**LLM не принимает решение о том, есть ли проблема** — это делает классификатор. LLM только формулирует уже вынесенный вердикт в человекочитаемом виде.

**Ограничения:** SLA p95 latency ≤ 10 секунд на анализ одного PR (сумма классификация + retrieval + генерация); бюджет токенов на комментарий — не более 300 токенов; кэширование шаблонов промптов по типу антипаттерна.

**Оценка качества текста:** офлайн — ROUGE-L и BERTScore на размеченном eval-сете (эталонные комментарии, написанные вручную); продуктовый proxy — доля комментариев, помеченных разработчиком как «helpful» (реакция thumbs up в GitHub).

---

### Вне MVP

С запасом на потом: multi-label классификация (один фрагмент — несколько антипаттернов), анализ динамики технического долга по истории репозитория, fine-tuning retrieval-модели, поддержка GitLab и Bitbucket, contextual bandit для оптимизации порога confidence под конкретную команду.

---

### Сводка метрик по компонентам

| Компонент | Offline (MVP) | Offline (пост-MVP) | Продукт / online |
|---|---|---|---|
| **Классификатор** | **F1-macro**, Precision/Recall по классам, MCC, confusion matrix | при переходе на multi-label: micro-F1, Hamming loss | доля принятых (resolved) комментариев; снижение плотности антипаттернов в следующих PR |
| **RAG / retrieval** | MRR, Recall@k на eval-сете | fine-tuned retrieval: nDCG@k | доля комментариев без follow-up вопросов от разработчика |
| **LLM-генерация** | ROUGE-L, BERTScore на эталонных комментариях | расширение eval-сета | «helpful»-реакции; **p95 latency ≤ 10 с**; стоимость токенов на PR |
| **Система в целом** | end-to-end тест на hold-out репозиториях | бенчмарк vs SonarQube на открытых проектах | время ревью senior-разработчиков; retention команд |

## 1.3 План проекта (Project Plan)

### Фаза 1. Business Understanding

На этом этапе фиксируем, что должен делать PRism:
- кто им пользуется и в каком сценарии;
- какие классы антипаттернов входят в MVP, какие — нет;
- что считается успехом: F1-macro ≥ 0.72 на hold-out set как порог выпуска модели в прод.

Фиксируем центральную постановку: **многоклассовая классификация** фрагментов кода → **RAG-обогащение** контекстом → **LLM-формулировка** комментария → GitHub inline review. Классификатор решает «есть ли проблема и какая», LLM только формулирует — эта граница не двигается в рамках MVP.

### Фаза 2. Data Understanding

- Разобрать GitHub API как основной источник: структура PR-диффов, формат review-комментариев, rate limits и квоты.
- EDA по собранному датасету: распределение классов, длины сниппетов, языки, качество авторазметки по ключевым словам.
- Зафиксировать план ручной верификации: объём (~3 000 примеров), инструмент (Label Studio), метрика согласия (Cohen's kappa).

### Фаза 3. Data Preparation

- Парсинг GitHub API + PyDriller: сбор пар (сниппет → комментарий) из публичных репозиториев.
- Авторазметка по ключевым словам в комментариях, фильтрация шума.
- Токенизация под CodeBERT (`RobertaTokenizer`), усечение до 512 токенов, padding.
- Разбиение train/val/test (70/15/15) со стратификацией по классам.
- Data augmentation для редких классов: синтетическая генерация примеров через LLM с ручной верификацией выборки.

### Фаза 4. Modeling

4.1. Обучение классификатора антипаттернов

- Baseline: TF-IDF + LogReg/RF, зафиксировать F1-macro как точку отсчёта.
- Основная модель: fine-tune CodeBERT, classification head поверх [CLS], CrossEntropy с class weights.
- Hyperparameter search через Optuna: lr, batch size, warmup ratio, weight decay.
- Трекинг всех экспериментов в MLflow: метрики, гиперпараметры, артефакты модели.
- Explainability: attention visualization и SHAP для примеров в дипломной работе.

4.2. RAG-пайплайн

- Индексация тестового репозитория: чанкинг по функциям, эмбеддинги, загрузка в Qdrant.
- Top-k retrieval, оценка на eval-сете.

4.3. Сборка end-to-end пайплайна

- FastAPI сервис: `/analyze` эндпоинт, очередь задач (Celery + Redis), ONNX-оптимизация инференса.
- GitHub App: webhook на `pull_request`, автопостинг review-комментариев через GitHub API.

### Фаза 5. Evaluation

- Офлайн-оценка классификатора: F1-macro, confusion matrix, анализ ошибок по классам.
- End-to-end тест: прогон на 5–10 реальных open-source репозиториях (Django, FastAPI, React), сравнение с SonarQube на тех же PR.
- Latency тест: p95 времени ответа при типичной нагрузке.
- Качество комментариев: BERTScore на eval-сете эталонных комментариев.

Оценка полного пути: `PR diff` → классификация → RAG → LLM → inline комментарий на GitHub → принят / отклонён разработчиком.

### Фаза 6. Deployment

- Docker-контейнеризация: отдельные образы для классификатора, RAG-сервиса, FastAPI, Celery worker.
- Деплой: Kubernetes (или Docker Compose на одном сервере для MVP).
- CI/CD: GitHub Actions — тесты → build → деплой → smoke-test на синтетическом PR.
- Мониторинг: Prometheus + Grafana (latency, throughput, error rate); Evidently AI — дрейф распределения предсказаний классификатора.
- Алёрт при деградации: если доля класса `CLEAN` превышает порог (сигнал, что модель перестала находить антипаттерны) — уведомление в Slack/email.
