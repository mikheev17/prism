# 2. Прототип PRism

## 2.1 Ключевая гипотеза (один сценарий, один сегмент, одна монетизация)

**Формулировка**

Если мы предлагаем **продукт** — PRism в объёме прототипа: GitHub App с автоматическим inline code review на базе **`CodeBERT`-классификатора** (5 из 8 классов антипаттернов) с **confidence threshold** как gate перед публикацией комментария и **LLM только для формулировки** уже вынесенного вердикта,

для **сегмента** — команды разработчиков **5–20 человек**, активно использующие GitHub и практикующие code review, пишущие на **Python**, с растущим техническим долгом и без выделенной роли архитектора,

в **сценарии** — разработчик открывает Pull Request в подключённом репозитории и **без каких-либо ручных действий** получает inline review-комментарии к конкретным строкам с типом проблемы и советом по исправлению — в том же UX, где команда уже работает,

то мы получим **метрику** — **helpful rate**: доля комментариев PRism, помеченных разработчиком как «полезно» (thumbs up в интерфейсе GitHub или через форму),

**не менее** — **40%** от всех опубликованных комментариев при **false positive rate ≤ 20%** по оценке команды,

**в течение времени** — **4 недели** после подключения первых репозиториев или до накопления **не менее 150 оценённых комментариев** (что наступает раньше),

**потому что** специализированная классификационная модель на CodeBERT способна выявлять смысловые и архитектурные антипаттерны, которые линтеры пропускают, а confidence threshold предотвращает спам низкокачественных комментариев — вместе это создаёт сигнал, который команда воспринимает как полезный, а не как раздражающий.

**Примечания.** Helpful rate считается только по комментариям с confidence выше порога; ниже порога комментарий не публикуется. Если к концу 4 недель число оценённых комментариев не достигло 150 — принимаем решение по накопленным данным, явно помечая его как ослабленную проверку гипотезы.

**Монетизация, которую проверяем:** командная подписка **per seat** — **$19/активный разработчик/мес** при annual billing (уровень Team, в одном ряду с CodeRabbit/Codacy). Метрика-прокси для прототипа — доля команд, выразивших готовность платить (устный интерес или предоплата) по итогам trial.

## 2.2 Ключевые метрики (продуктовые и технические)

Ниже — **целевые ориентиры для прототипа**. Конкретные числовые пороги confidence per-class калибруем по первой неделе живых PR; до этого колонка «цель» — рабочая гипотеза для команды.

### Продуктовые

| Метрика | Что считаем | Baseline | Способ измерения | Частота | Цель прототипа (ориентир) |
|---------|-------------|----------|------------------|---------|---------------------------|
| **Helpful rate** | Доля опубликованных комментариев, помеченных разработчиком как «полезно» | 0 до первых данных; затем среднее по неделе | Thumbs up/down в GitHub Review или простая форма обратной связи | Ежедневно агрегат + еженедельный отчёт | **≥ 40%** при стабильном N |
| **False positive rate** | Доля комментариев, оценённых командой как «неверно / нерелевантно» | 0 до первых данных | Thumbs down + опциональный текст обратной связи | Еженедельно | **≤ 20%** |
| **Activation rate** | Доля PR, получивших хотя бы один опубликованный комментарий | Зависит от порогов confidence | Лог webhook + статус публикации через GitHub API | Еженедельно | Укладывается в ожидаемый диапазон (60–80% PR); нет «тишины» по качественному разбору |
| **Конверсия в оплату** | Trial → выраженная готовность платить или предоплата | После первых ~5–10 команд | Прямые переговоры + трекер в CRM/таблице | По окончании каждого trial | Зафиксировать **верхнюю границу воронки** для следующего этапа |

### Технические

| Метрика | Что считаем | Baseline | Способ измерения | Частота | Цель прототипа |
|---------|-------------|----------|------------------|---------|----------------|
| **F1-macro классификатора** | Офлайн-качество CodeBERT на hold-out test set (15%) | TF-IDF baseline ~0.35 | Стандартный ML-eval пайплайн | При каждом изменении модели или раз в спринт | **≥ 0.60** (MVP-порог выпуска в прод — 0.72) |
| **p95 latency на PR** | Время от получения webhook до публикации последнего комментария | Измерить на staging с типичным PR (~10 файлов) | Логи FastAPI (`webhook_received` → `comment_posted`), Prometheus | Ежедневно при активной разработке; еженедельно в стабильной фазе | **≤ 10 с** p95; иначе явный UX «ожидание» |
| **Ошибки API / падения** | HTTP 5xx, таймауты, ошибки при генерации комментария | После стабилизации — доля от запросов | Логи бэкенда + Sentry | Ежедневно | **< 1%** неуспешных генераций при нормальной нагрузке прототипа |
| **Стоимость токенов на PR** | Сумма токенов LLM × тариф / число проанализированных PR | Первые 50 PR | Billing провайдера LLM + счётчик токенов в логах | Еженедельно | Укладывается в **предельный COGS** на PR (фиксируется до запуска; ориентир ≤ $0.05 за PR при GPT-4o mini) |

## 2.3 Что входит в прототип и что намеренно не делаем

### Входит в прототип

- **GitHub App** с webhook на событие `pull_request` — автоматический запуск анализа без ручных действий со стороны команды.
- **CodeBERT-классификатор** на **5 классах** из 8: `SOLID_VIOLATION`, `N_PLUS_ONE`, `SECURITY_MISCONFIG`, `EXCESSIVE_COMPLEXITY`, `CLEAN`. Редкие классы (`RACE_CONDITION`, `DEAD_CODE`) и `MISSING_ERROR_HANDLING` — вне прототипа (недостаточно данных для уверенного F1).
- **Confidence threshold per-class**: комментарий публикуется только при уверенности выше порога — ключевая защита от спама ложными срабатываниями.
- **LLM-генерация комментария** (GPT-4o mini или Claude Haiku через API) по шаблону: тип антипаттерна + сниппет → объяснение + совет. LLM не принимает решения о наличии проблемы.
- **Публикация inline review-комментариев** через GitHub API к конкретным строкам PR.
- **Форма обратной связи**: thumbs up/down на каждый комментарий для сбора helpful rate.
- **Поддержка Python-only** на прототипе.
- **Сбор событий**: webhook получен, сниппеты классифицированы, комментарий опубликован / не опубликован (confidence ниже порога), получена оценка.

### Намеренно не делаем в прототипе (и почему)

| Исключение | Причина |
|------------|---------|
| **RAG-контекст из кодовой базы (Qdrant)** | Добавляет 3–4 недели инфраструктурной работы; проверяем сначала, даёт ли базовый классификатор полезный сигнал без контекста репозитория. |
| **Поддержка Java и TypeScript** | Объём качественно размеченных данных для одного языка накапливается в 3× быстрее; смешение языков на прototипе размывает выводы о качестве модели. |
| **Dashboard и история PR** | Нет накопленных данных; ценность динамики технического долга не подтверждена — оставляем на пост-MVP. |
| **Multi-label классификация** | Требует отдельной разметки и иных метрик (micro-F1, Hamming loss); не влияет на проверку ключевой гипотезы. |
| **Классы RACE_CONDITION, DEAD_CODE, MISSING_ERROR_HANDLING** | Недостаточно размеченных примеров для уверенного F1 на прototипе; добавление «слабых» классов снизит воспринимаемое качество и helpful rate. |
| **Kubernetes и production infra** | Docker Compose на одном Hetzner-сервере достаточен для нагрузки прoтoтипа (3–5 команд); Kubernetes — при подтверждённом росте. |
| **Полноценная биллинг-система** | Для проверки монетизации достаточно Stripe Checkout или ручного учёта интереса; строить биллинг до подтверждения готовности платить — преждевременно. |

## 2.4 Готовые блоки vs. своё

### Берём готовое

| Блок | Зачем |
|------|-------|
| **`microsoft/codebert-base` (HuggingFace, MIT)** | Предобучен на коде — сокращает cold start на классификации на месяцы; лицензия позволяет коммерческое использование. |
| **LLM API (GPT-4o mini / Claude Haiku)** | Генерация текста комментария — commoditized задача; строить LLM с нуля не имеет смысла. |
| **GitHub App SDK + PyGitHub** | Авторизация, webhook-обработка, inline comments через готовый API — не наша продуктовая дифференциация. |
| **FastAPI + Celery + Redis** | Стандартный стек для асинхронной очереди задач; не изобретаем велосипед на инфраструктурном уровне. |
| **Label Studio (self-hosted)** | Зрелый open-source инструмент для ручной верификации разметки; альтернативы дороже или сложнее в деплое. |
| **MLflow (self-hosted или HuggingFace Spaces)** | Трекинг экспериментов, версионирование артефактов модели — стандарт для ML-проектов. |
| **Sentry** | Мониторинг ошибок бэкенда без разработки своего алёртинга. |

### Делаем сами (критично)

| Компонент | Почему критично своё |
|-----------|----------------------|
| **Пайплайн авторазметки PR-комментариев** | Специфичен для нашего датасета: сопоставление комментарий → строка диффа → сниппет, regex-фильтрация шума — готового решения нет; качество разметки напрямую определяет F1 модели. |
| **Classification head + fine-tuning loop** | 5-классовая голова поверх [CLS]-токена с weighted CrossEntropy — это и есть суть продуктовой дифференциации; generalist-модели не дают нужной специализации. |
| **Confidence threshold per-class** | Определяет баланс между activation rate и false positive rate; пороги специфичны для наших классов и данных — нельзя взять из коробки. |
| **Промпт-шаблоны по типу антипаттерна** | LLM получает структурированный контекст (тип + сниппет + confidence) — качество формулировки и отсутствие галлюцинаций зависит от нашего промпта; шаблоны являются частью продуктового IP. |
| **Схема логирования событий** | Без связки `webhook → классификация → публикация → оценка` невозможно считать ключевые метрики и итерировать модель по обратной связи. |

## 2.5 Главный риск, который проверяет прототип

**Риск:** inline-комментарии PRism воспринимаются командой как **шум, а не как помощь** — даже при технически корректной классификации.

Если confident predictions классификатора не соответствуют тому, что опытные разработчики считают реальной проблемой, или если формулировки комментариев слишком generic и не несут конкретной ценности — команды начнут dismiss-ить или игнорировать комментарии. Это разрушает retention-механику (подписку) быстрее, чем любой технический сбой: GitHub уже показывает комментарии, и если они раздражают — команда отключит App.

Этот риск нельзя проверить офлайн на метрике F1-macro: модель с F1 0.65 может давать helpful rate 60%, а модель с F1 0.70 — helpful rate 20%, если уверенные ошибки систематически попадают в «чувствительные» паттерны, о которых команда уже знает.

Если прototип подтверждает риск (helpful rate < 25% при неделе 4) — фундаментальная проблема в релевантности классов или качестве формулировок, а не в маркетинге. Следующий шаг — custdev с конкретными командами по каждому типу dismiss-а, прежде чем итерировать модель.

## 2.6 Конечный формат и вид прoтoтипа

- **Для разработчика:** установка GitHub App на репозиторий в один клик через GitHub Marketplace (или прямая ссылка на период закрытого теста); при открытии любого PR — автоматическое появление inline review-комментариев к конкретным строкам; каждый комментарий содержит тип антипаттерна, объяснение проблемы, конкретный совет по исправлению и confidence score; кнопки 👍 / 👎 на каждом комментарии для оценки полезности.
- **Для команды:** никаких обязательных настроек после установки App; опциональный `.prism.yml` в репозитории для тонкой конфигурации порогов и языка комментариев.
- **Для команды PRism:** задеплоенный сервис с закрытым доступом (whitelist репозиториев на период теста), конфиг confidence thresholds **без передеплоя модели**, дашборд с метриками из §2.2 (Grafana + ручная таблица на первое время).
- **Артефакт завершения:** короткий отчёт (1–2 страницы): helpful rate и false positive rate по классам, activation rate, список решений по порогам, сводка качественной обратной связи от команд, «делать / не делать» для перехода к полному MVP.

## 2.7 Критерии остановки теста прoтoтипа

Останавливаем эксперимент и принимаем решение **go / iterate / pivot**, если выполняется хотя бы одно из условий ниже.

**По сроку и объёму данных**

Прошло **4 недели** с момента стабильного получения PR в подключённых репозиториях или накоплено **≥ 150 оценённых комментариев** — в зависимости от того, что наступает раньше (порог уточняется под реальный темп PR в тестовых командах).

**Остановка с позитивным сигналом (go к полному MVP)**

- Helpful rate **≥ 40%** и false positive rate **≤ 20%** при стабильном N.
- F1-macro классификатора **≥ 0.60** на hold-out set.
- **≥ 2 команды** из тестовых выразили готовность платить по итогам trial.
- P95 latency **≤ 10 с** при типичной нагрузке.

**Остановка с частичным сигналом (iterate — правим подход)**

- Helpful rate в диапазоне **25–40%** или false positive rate **20–35%**: переформатируем промпты, снижаем пороги публикации по проблемным классам, анализируем паттерны dismiss-а.
- F1-macro **0.50–0.60**: итерируем разметку и аугментацию данных по слабым классам.

**Остановка с негативным сигналом (pivot — переосмысление до следующей итерации)**

- Helpful rate **< 25%** на неделе 4 при достаточном N — гипотеза не подтверждена; необходим custdev по каждому типу dismiss-а перед следующей итерацией.
- F1-macro **< 0.45** после 3 итераций обучения с разными конфигурациями — пересматриваем датасет, разметку и постановку классификационной задачи.
- Команды системно отключают App или перестают открывать PR в подключённых репозиториях — сигнал раздражения, требующий качественного исследования.

**Этические и технические стоп-критерии**

- Серия инцидентов с **ошибочным или вводящим в заблуждение контентом** в комментариях (галлюцинации LLM, некорректные security-предупреждения) без возможности быстро поднять порог confidence — пауза до исправления guardrails и переработки промптов.
